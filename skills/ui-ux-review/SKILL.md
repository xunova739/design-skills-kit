# UI/UX Review Router

把模糊的“好不好看、好不好用”翻译成可验证的审核任务。先看真实界面和真实流程，再给结论；不要只读代码后凭感觉评价。

## 先确定审核对象

从用户提供的材料中自行确认四件事：

1. 谁在使用。
2. 他要完成什么任务。
3. 审核哪个页面、组件或完整流程。
4. 当前可用证据是什么：运行中的产品、URL、本地项目、Figma、截图、设计稿或代码。

只有会明显改变审核范围时才问一个问题。目标和主任务已能从上下文判断时，直接开始。

## 证据门禁

- 有运行中的产品或本地前端：真实点击主流程，逐步截图，并检查控制台、加载、校验、失败和完成反馈。
- 有 Figma 或设计稿：读取实际画面、组件和关键状态；不要只根据图层名评价。
- 有参考设计和已实现页面：统一视口、内容、主题和状态后再比较。
- 只有截图：可以审核可见的视觉层级、文案、可见交互暗示和明显可访问性风险，但必须写成“截图可见风险”或“待实测”；不能声称已经验证点击成本、真实目标尺寸、键盘、错误恢复或完整流程。
- 只有代码：可以做实现风险预审，但不能把它包装成完整 UI/UX 审核。

每条结论必须绑定当前审核中看到的页面、步骤、状态、截图或行为。旧截图和历史印象不能冒充本轮证据。

在任何发现之前，先明确写出：

```text
审核类型：实测流程审核 / 设计稿对照 / 截图预审 / 代码预审
已验证：本轮真正看过或操作过的内容
未验证：点击、键盘、错误恢复、状态或设备中尚未检查的内容
```

截图预审中的每条交互发现必须按“可见现象 -> 潜在风险 -> 验证方法”表达。不能用“用户会误触、用户找不到、点击成本高”这类已经证实的口吻。

## 路由

按用户真正关心的问题选择最小能力组合；交接别名见 [ALIASES.md](ALIASES.md)，仅在需要调用时解析。

| 用户问题 | 主路由 | 补充能力 |
|---|---|---|
| 用户流程绕、入口难找、点击费劲、下一步不清楚、表单难填 | `@product-audit` | 本地 Web 用 `@web-test` 或浏览器采集真实交互证据 |
| 页面不好看、层级乱、模板味重、想知道为什么丑 | `@product-audit` 的单屏审查 | 用户明确要打分或五维报告时才用 `@critique` |
| 设计稿与实现不一致 | `@design-qa` | 需要严格截图对照信号时追加 `@visual-compare` |
| 只要求严格判断“像不像参考图” | `@visual-compare` | 不把它扩展成用户流程审核 |
| 审核后还要直接修 | 先完成上述审核 | 营销页/作品集可用 `@marketing-design`；一般前端可用 `@frontend-design`；产品 UI 优先沿用现有设计系统 |
| 审核结论已具体到“某个 React Bits 组件能解决某个已验证问题” | `@react-bits` | 只在证据化后单向交接；React Bits 不得反向重新定义审核范围 |

如果 Product Design 的专职 skill 当前不可用，使用浏览器或测试工具采证，再读取 [review-checklist.md](references/review-checklist.md) 完成同等结构的审核。不要因为某个子 skill 不可用就跳过证据门禁。

有 Web 源码或运行页面、需要实现定位时，按需读取 [web-interface-checks.md](references/web-interface-checks.md)，补查语义、对比度、恢复、布局、性能与本地化；只选适用项，保持上述证据门禁。

## 审核顺序

1. 跑通主任务，从入口走到完成或失败。
2. 审核结构问题：入口、信息架构、主次关系、步骤数量、反馈和恢复。
3. 审核视觉问题：层级、密度、排版、颜色、组件一致性、品牌感和模板味。
4. 审核状态：默认、加载、空、成功、失败、禁用、过期或旧数据失效。
5. 审核跨设备与可访问性：移动端、键盘、焦点、目标尺寸、对比度、缩放和减少动效。
6. 区分根因与表面装饰，按用户影响给 P0/P1/P2。
7. 用户要求整改时，修复后用同一任务、视口和状态复测，不以“代码改完”代替验收。

## 输出契约

默认先讲业务结论，不把文件路径、组件名和英文术语堆在正文里。

```markdown
审核类型：...
已验证：...
未验证：...

总体判断：用户能否顺利完成主任务，最主要的阻力是什么。

P0 必须先修
- 用户在哪一步遇到什么问题
- 对任务完成或业务结果的影响
- 建议怎么改
- 证据来自哪个步骤或画面

P1 明显改善
...

P2 视觉润色
...

做得好的地方
...

证据边界
- 哪些已经真实点击或测过
- 哪些只是截图可见风险
- 哪些状态还没有证据
```

“证据边界”是必填项，即使没有缺口也要明确写“已验证范围”。截图推测的交互风险不能直接定为 P0；除非画面本身已经明确遮挡或阻断核心操作，否则标为待实测的 P1/P2 风险。

将技术细节放在最后的“实现定位”中，仅在用户要改代码或追查证据时给出。每个路径或标识后先写业务含义，例如“管理员工作台（实现位置：...）”。

## 硬规则

- 不用“感觉不高级”“可以更精致”这类无证据判断。
- 不把视觉好看等同于可用，也不把流程能走通等同于设计合格。
- 不用 React Bits、渐变、动效、阴影或更多卡片掩盖结构问题。
- 不把截图审核写成完整 WCAG 合规结论。
- 不把截图中“看起来偏小、偏弱、可能难找”写成已经证实的点击困难、误触或任务失败。
- 不省略证据边界，不用肯定语气包装未经运行态验证的推测。
- 截图预审不输出“用户会怎样”的行为结论，只输出可见现象、潜在风险和验证方法。
- 不在用户只要求审核时擅自修改产品；用户同时要求整改时，审核先行，再改再复测。
- 不平均稀释严重问题。核心任务被阻断就是 P0，即使其他页面很漂亮。

## 触发样例

应触发：

- “这个后台做得一坨，帮我看看为什么这么丑。”
- “从候选人筛选到发起面试走一遍，哪里点起来费劲？”
- “审一下这个 Figma，用户第一次来会不会迷路？”
- “实现和设计稿差多少，按优先级告诉我怎么改。”
- “移动端按钮是不是难点，错误态和空态也一起看。”

不应触发：

- “从零给我做一个落地页。”应走创建/设计入口。
- “安装 BlurText。”应走 `@react-bits`。
- “把这张海报导出成 PNG。”应走对应视觉产物工具。
